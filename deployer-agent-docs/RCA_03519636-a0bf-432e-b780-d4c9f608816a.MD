# RCA — videomaker-dl: production `public/` assets 404 (covers, local videos, PDF)

## Problem statement
Next.js 15 portfolio (next.config.js has `output: 'standalone'`). In preview everything works; on the published production site the cover images don't appear and some videos don't play. Local static assets live under `/app/public` (`/covers/*.jpg`, `/videos/*.mp4`, `/docs/cv-daniele-leonzi.pdf`). Remote assets (customer-assets CDN mp4/webp, YouTube) work. Asked to check live HTTP status of specific assets + whether Range requests return 206.

## What I could and could not verify
- **Live HTTP status checks could NOT be performed.** The deployment is currently `status=deleted`, `suspension_reason=negative_credit`. `preview_health_check` returns `no_active_url — deployment is not active — nothing is serving on the URL`. So right now the ENTIRE production site is down (not just the assets), and I cannot report the per-asset status codes or Range (206) behavior you asked for — nothing is serving to probe.
- Eph sandbox would not start (deployment infra torn down since it's deleted), so I diagnosed from the build logs of the active/last-successful run `03519636-a0bf-432e-b780-d4c9f608816a` instead.

## Root cause (PROVEN from build logs)
The platform's Next.js runner (final) Docker stage copies the standalone server and static output but **never copies the `public/` directory into the runtime image**. Build log, runner stage (6 steps total):

```
#19 [runner 3/6] COPY --from=builder /app/.next/standalone ./
#20 [runner 4/6] COPY --from=builder /app/.next/static ./.next/static
#21 [runner 5/6] COPY entrypoint.sh /app/entrypoint.sh
#22 [runner 6/6] RUN chmod +x /app/entrypoint.sh
```

There is no `COPY --from=builder /app/public ./public`. With `output: 'standalone'`, Next.js intentionally does NOT include `public/` (or `.next/static`) inside `.next/standalone` — the docs require copying both manually. The template copies `.next/static` but omits `public/`. Result: the production standalone server has no `public/` folder and returns **404 for every file under `/public`** — `/covers/*.jpg`, `/videos/*.mp4`, `/docs/cv-daniele-leonzi.pdf`. Remote CDN/YouTube assets are unaffected because they are not served from `public/`. This exactly matches the reported symptom (missing covers, local videos not playing, remote videos fine).

## Size-limit hypothesis — DISPROVEN
All public files, including the 48 MB `video-vsl.mp4`, were present in the build context (source zip extraction in the build log):
```
inflating: /workspace/public/covers/p1.jpg
inflating: /workspace/public/covers/daniele-portrait.jpg
inflating: /workspace/public/videos/reel-rotonda.mp4
inflating: /workspace/public/videos/video-vsl.mp4
inflating: /workspace/public/docs/cv-daniele-leonzi.pdf
```
No per-file size filtering occurred on pull/upload. The failure is purely the missing `public/` COPY in the runner stage — not a size cap. (So the 48 MB video and a 5 KB jpg fail identically, both 404.)

## Fixes
1. **Settle the negative credit balance (User → Deployment is suspended).** The deployment is `deleted`/suspended for `negative_credit`; nothing serves and no redeploy can run until this is resolved. This is the immediate, top-priority blocker and the reason live checks are impossible right now.
2. **Add `public/` to the Next.js standalone runner image (build-manifest / Platform template gap).** Once the deployment is reinstated, a redeploy needs the runner stage to include:
   ```dockerfile
   COPY --from=builder /app/public ./public
   ```
   (alongside the existing `.next/standalone` and `.next/static` copies). This is a Dockerfile manifest override the deployer applies on redeploy; it should also be fixed in the stock `nextjs_mongo_shadcn_base_image` template, since it breaks any standalone Next app serving files from `public/`. After the fix, verify `/covers/p1.jpg`, `/videos/reel-rotonda.mp4` (plus Range `bytes=0-1000` → 206) and the PDF.

## Note on Range/206
Range (206) behavior could not be tested (site down). Once `public/` is copied in, the Next.js standalone static file server handles Range requests for mp4s normally; if large-video playback still misbehaves after the fix, re-test Range specifically.
